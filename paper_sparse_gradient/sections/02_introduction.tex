\section{Introduction}

Modern AI training workloads are not composed only of dense matrix multiplication, convolution, or attention kernels. Many practical models also contain sparse or irregular components whose performance is shaped by index distributions, memory access patterns, and reduction behavior. This is especially visible in recommendation and sparse-feature models, where large embedding tables are used to represent categorical identifiers and where training efficiency depends on both dense neural-network computation and memory-intensive embedding operations \citep{gupta2020architectural,acun2021training}. Recent work on large-scale embedding optimization further shows that embedding access patterns, repeated indices, and gradient processing remain important systems-level concerns in recommendation-model training \citep{liu2024embark}.

A central operation in such workloads is sparse-index gradient accumulation during backpropagation. In the forward pass, indexed operations such as embedding lookup gather rows from a parameter table. In the backward pass, gradients associated with those indexed rows must be routed back and accumulated into the corresponding parameter-gradient structure. When the same index appears multiple times in a batch, several gradient contributions target the same destination row. This creates an indexed aggregation problem rather than a purely dense tensor operation. The cost of this aggregation can depend on the number of rows, number of indices, feature dimension, index skew, duplicate-index frequency, memory layout, and the CUDA execution path selected by the framework.

From a parallel-computing perspective, these operations are instances of irregular indexed reduction: many source vectors update a smaller set of destination rows, and duplicate or skewed indices create contention, ordering, and memory-access effects. This makes stack-sensitive performance behavior a performance-portability concern for high-level GPU tensor APIs, beyond API convenience in machine-learning code.

PyTorch exposes several high-level APIs that can express related accumulation-style behavior. The \texttt{torch.nn.Embedding} module provides a standard embedding-table abstraction and supports sparse gradients with respect to embedding weights in selected configurations \citep{pytorchStableEmbedding}. Tensor-level APIs such as \texttt{index\_add\_}, \texttt{scatter\_add}, and \texttt{scatter\_add\_} also describe indexed accumulation or scatter-add semantics \citep{pytorchStableIndexAdd,pytorchStableScatterAdd,pytorchStableTensorScatterAdd}. From the perspective of a model developer, these APIs may appear to represent closely related ways of accumulating indexed values. However, high-level semantic similarity does not imply that the same CUDA kernels, memory behavior, or performance characteristics are used internally.

This distinction matters because GPU execution is asynchronous, parallel, and sensitive to reduction order, memory access, and synchronization behavior. PyTorch documentation notes that CUDA execution is asynchronous relative to the CPU, which makes synchronization-aware timing necessary for accurate measurement \citep{pytorchStableCUDASemantics}. PyTorch also documents nondeterminism concerns for selected CUDA operations and reproducibility settings \citep{pytorchStableReproducibility}. At the same time, CUDA event timing and profiler-based kernel attribution provide practical tools for separating clean latency measurements from diagnostic execution-path analysis \citep{nvidiaCUDAEvents,pytorchStableProfiler,nvidiaNsightCompute}. These properties make sparse-index accumulation a suitable target for controlled benchmarking and profiling.

Prior work has studied sparse GPU kernels, irregular graph and sparse-matrix workloads, recommendation-system architectures, and large-scale embedding optimization \citep{gale2020sparse,wang2016gunrock,huang2020gespmm,gupta2020architectural,acun2021training,liu2024embark}. These studies establish that sparse and irregular workloads are important and that their performance depends on memory behavior, data distribution, and execution strategy. However, they do not directly answer a narrower practical question faced by PyTorch users: how do standard PyTorch CUDA paths such as \texttt{index\_add}, \texttt{scatter\_add}, and \texttt{Embedding.backward} compare under matched sparse-index gradient accumulation workloads?

This paper addresses that question through a controlled empirical study of sparse-index gradient accumulation during backpropagation-style computation. The study evaluates standard PyTorch CUDA paths rather than custom CUDA kernels. It first calibrates the benchmark protocol and validation rules, then performs a matched grid-level timing comparison, uses representative profiler runs to relate timing behavior to CUDA execution paths, and finally adds a small training-step proxy to examine whether isolated sparse-index accumulation behavior remains visible in a broader backward-style computation. The main systems contribution is a reproducible performance characterization and measurement-backed interpretation framework for workload-, scope-, and stack-dependent behavior, culminating in a tie-aware selection protocol.

The paper makes five contributions:
\begin{itemize}
\item A correctness-gated, reproducible comparison of three standard PyTorch CUDA sparse-index accumulation paths: \texttt{index\_add}, \texttt{scatter\_add}, and \texttt{Embedding.backward}.
\item Evidence of workload-, scope-, and stack-dependent behavior across the GTX1650Ti and hosted Colab T4 stacks, using matched isolated benchmarks and a backward-style proxy.
\item Profiler-backed evidence of distinct CUDA execution-path compositions, interpreted at the stack level rather than as isolated hardware causality.
\item Threshold-sensitivity and descriptive bootstrap checks, winner maps, and regret/minimax analyses that contextualize practical ties and quantify static-selection costs.
\item A measurement-backed, tie-aware selection protocol for comparing candidate paths under the target workload and execution stack.
\end{itemize}
