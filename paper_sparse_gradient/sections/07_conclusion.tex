\section{Conclusion}
\label{sec:conclusion}

This paper presented a reproducible performance characterization of three standard PyTorch CUDA paths for sparse-index gradient accumulation in backpropagation: \texttt{index\_add}, \texttt{scatter\_add}, and \texttt{Embedding.backward}. The study focused on a recurring systems problem in embedding-heavy and sparse-feature training workloads: repeated indices route multiple gradient contributions to shared parameter rows, so the cost of the backward pass can depend not only on tensor semantics but also on the CUDA execution path selected by the framework.

The results show that semantically related APIs do not provide interchangeable performance behavior. Across the tested GPU/software stacks, matched controlled workloads exhibited workload-, scope-, and stack-dependent outcomes, with no universal fastest API in the saved observations. The isolated grid and the backward-style proxy also led to different practical conclusions, showing that isolated sparse-index accumulation rankings should not be transferred mechanically to broader backpropagation-style computation. Profiler summaries explain this behavior at the execution-path level: the direct tensor APIs were dominated by their corresponding accumulation kernels, whereas \texttt{Embedding.backward} followed a multi-kernel path that included accumulation and sorting or segmentation-related components. This supports a stack-level execution-path interpretation without claiming isolated GPU-architecture causality.

The additional descriptive analyses refine the practical meaning of these results. Threshold-sensitivity checks, bootstrap intervals, and winner maps show that both decisive winners and near-tie regions are part of the observed behavior. Regret analysis further shows why a tie-aware interpretation is necessary: static API selection can be costly, the lowest-mean-regret static choice changes with stack and scope, and even the smallest observed worst-case static regret reaches 145.0\%. Thus, the absence of a universal default is not merely a conservative statement; it follows from the measured cost of choosing one path statically across saved observations. At the same time, practical ties among leading paths do not imply that all candidate APIs are interchangeable.

The practical output of the study is therefore not a universal ranking of \texttt{index\_add}, \texttt{scatter\_add}, and \texttt{Embedding.backward}, but a measurement-backed, tie-aware selection protocol. Candidate paths should be measured under the target sparse workload and execution stack; small differences should be retained as practical ties rather than forced into artificial rankings; isolated rankings should be checked against a broader backward-style scope when the operation is performance-critical; and profiler evidence should be used to inspect whether timing differences correspond to distinct CUDA execution paths. This guidance remains bounded by the study design: controlled workloads, representative profiling cases, two GPU/software stacks, and a synthetic proxy. Future work should extend the characterization to fuller training loops, real index traces, additional stacks, sparse optimizer behavior, lower-level profiling, and possibly lightweight calibration or autotuning tools built on the same measurement-backed protocol.
